Users App Test Framework

A practical guide to how this TypeScript framework configures environments, runs browser and API tests, manages test data, validates API responses, organizes its source files, and generates tests from requirements.

Playwright Test TypeScript Chromium REST · GraphQL · OpenAPI Zod API validation axe-core accessibility Claude Code orchestrator

Overview

The framework tests the Users App at the BASE_URL selected for a run. Browser tests cover the home page, login flow, users screen, accessibility, network-failure states, and complete user journeys. API tests cover the REST endpoints, the GraphQL API, and the published OpenAPI document, and validate response payloads at runtime.

UI tests

Located in tests/ui/; executed in Chromium (Firefox, WebKit, and a Pixel 7 mobile viewport are configured but disabled). Includes axe accessibility scans and network-mocked API failures, slow responses, and row actions.

API tests

Located in tests/api/; executed once in the dedicated api project. Covers REST, GraphQL, and the published OpenAPI contract. Data-reset specs in tests/api/destructive/ run last, in the api-destructive project.

Shared code

Page objects, fixtures, test data, factories, API schemas, and environment checks are kept in focused modules.

The Users App is included in app/ as a Git submodule. Initialize it with git submodule update --init --recursive. For loopback targets under TEST_ENV=local or TEST_ENV=test, Playwright starts it with npm --prefix app start and waits for BASE_URL. Remote test, development, and staging targets must already be reachable.

The app is force-updated before local runs. The pre hooks of npm test, test:local, test:test, test:api, test:headed, test:ui, and test:debug run scripts/update-app.mjs. It discards any local edits in app/, checks out the latest commit of the submodule's tracked branch (main, from .gitmodules), and runs npm ci --prefix app only when the app's dependencies changed. Fix app defects upstream in users-app-demo, not in app/. If the fetch fails or times out, the run continues on the current checkout. Set SKIP_APP_UPDATE=1 to skip the update; it is also skipped when CI is set, because the workflow updates the submodule itself. test:dev and test:staging have no update hook because they target remote apps.

Quick start

  1. Install Node.js 20.19+, 22.13+, or 24+ and npm.
  2. Install framework and bundled app dependencies, then the three browser engines.
  3. Copy an environment example and set the application URL and credentials.
  4. Run the desired test command; Playwright starts the bundled app for loopback targets.
git submodule update --init --recursive
npm ci
npm ci --prefix app
npx playwright install chromium
cp env/.env.example env/.env.local
npm run test:local

For API tests that create or delete users, use a loopback URL with TEST_ENV=local or a dedicated, disposable TEST_ENV=test target with an explicit hostname allowlist.

How a test run works

  1. Update app.
    The npm pre hook moves app/ to the latest upstream commit (skipped in CI or with SKIP_APP_UPDATE).
  2. Select environment.
    TEST_ENV chooses the matching env/.env.* file; an unknown value fails fast.
  3. Resolve URL.
    BASE_URL is required except for the local default.
  4. Start local app.
    Loopback targets in the local or test environment start app/; local runs reuse a responding server.
  5. Authenticate once.
    When credentials are set, the setup project logs in and saves .auth/user.json for the browser projects.
  6. Run projects.
    API specs run once in the api project; UI specs run in four browser projects; api-destructive runs last.
  7. Set up fixtures.
    Each test receives only the page objects, data, and API client it requests.
  8. Capture diagnostics.
    Failures retain screenshots and video; traces are collected on retries.
  9. Update history.
    Final outcomes update per-test pass rates and the standalone cumulative report.

playwright.config.ts defines projects, reporters, retries, browser settings, output locations, and environment loading. In CI, retries are set to 2 and test.only is rejected; locally there are no retries.

Fixtures and lifecycles

API fixtures

  • usersApi reads credentials and authenticates with POST /api/login.
  • graphqlApi authenticates the same way and sends queries and mutations to /graphql.
  • testData provides shared, read-only reference values.
  • apiTestUser creates a uniquely named user for one test and deletes it in teardown.

API fixtures are defined in tests/api/fixtures.ts. The API fixture is lazy: it does not log in or create a user unless a test requests it.

UI fixtures

  • loginPage and usersPage construct page objects for the current test's page.
  • The setup project logs in once and saves the app's local-storage token to the ignored .auth/user.json file.
  • authenticatedUsersPage opens the users screen using the saved state; each test still receives an isolated browser context.
  • Login-flow tests continue to navigate and submit the login form directly.
  • usersApiMock mocks users-API endpoints with page.route(): canned responses, network failures, and requests held back to test slow responses.
  • makeAxeBuilder returns a factory for an axe-core AxeBuilder preconfigured with the WCAG 2.1 A/AA tags (wcag2a, wcag2aa, wcag21a, wcag21aa).

UI fixtures extend the API fixtures in tests/ui/fixtures.ts. Authenticated tests are skipped when credentials are not configured.

API client and response validation

UsersApiClient centralizes authenticated requests for list, search, count, create, bulk create, retrieve, update, delete, and data-reset operations. Its successful JSON responses pass through parseApiResponse.

Runtime contracts are declared with Zod in tests/api/utils/schemas.ts: login API key, individual user, user list, user count, confirmation message, and the GraphQL response envelope. A response with an unexpected status, invalid JSON, or invalid payload shape fails with endpoint context. Unmodeled user fields are stripped from the parsed result.

API scenarios live in tests/api/users.api.spec.ts. They verify listing, search, count, retrieval, update, and deletion. CRUD tests use a generated user and are tagged @test-data.

GraphqlClient wraps every query and mutation in the app's GraphQL schema; users.graphql.spec.ts covers them, including cross-checks against the REST API.

openapi.contract.spec.ts reads the OpenAPI document that Swagger UI embeds in /api-docs/swagger-ui-init.js. It checks that the documented operations match usersApiOperations in the REST client, that the API-key header matches, and that every documented JSON response schema has the same fields as the Zod schema the tests use.

Tests for behaviour the app does not implement yet use test.fail() with an app-defect annotation. They report as expected failures and fail once the app is fixed, as a reminder to turn them into ordinary tests. Current defects: GraphQL updateUser and bulkAddUsers throw, /graphql needs no API key, and the OpenAPI document omits some statuses and marks /login as needing an API key.

Data reset: PUT /users/reset-data deletes every user added since startup, including users other tests are using. Its spec lives in tests/api/destructive/ and runs in the api-destructive project, which waits for every other project and is skipped if any of them has a failing test.
API contract note: The app's current raw user response includes a password property. The test schema does not expose that unmodeled property, but the application should avoid returning credentials in API responses.

Test data and safety rules

  • tests/data/users.ts contains typed reference data.
  • createUniqueUserData generates collision-resistant users for CRUD tests.
  • environment.ts reads credentials and guards mutation targets.
  • @test-data marks tests that create or delete application records.

The apiTestUser fixture creates and cleans up records only for loopback hosts under TEST_ENV=local or hostnames listed in TEST_DATA_ALLOWED_HOSTS under TEST_ENV=test. Development and staging scripts exclude tests tagged @test-data. Do not configure a production host as a test-data target.

Cumulative test history

Each Playwright run writes raw JSON results to test-results/results.json, updates the local .playwright-history/history.json store, and generates reports/test-history-report.html plus separate per-test history and recent runs pages under reports/, linked from the report header. The standalone HTML pages can be regenerated with npm run test:history:report.

  • Tests are identified by project, spec path, and full title path, so moving a test's source line does not reset its history.
  • Pass rate is passed divided by passed plus failed; skipped tests are shown separately and excluded.
  • A pass after a retry counts as passed and is also marked flaky.
  • Per-test totals are all-time; the latest 100 run summaries and 30 outcomes per test are retained.
  • The metrics landing page includes KPI cards, a pass-rate trend for up to 12 runs, and the latest run's outcome breakdown.

Use the report controls together to search scenario titles, spec paths, projects, and tags; filter by UI, API, or E2E category; select a latest status or a tag; and reset all filters. The Flaky status isolates tests whose latest result passed after retry.

The local history directory and generated HTML are Git-ignored. CI restores and updates history.json on the dedicated test-history branch, and uploads the HTML report pages with the run artifacts. The first non-PR run creates the branch. Repository Actions settings must allow the workflow's contents: write permission; pull-request runs do not write to the branch.

Adding tests

UI test

  1. Add a spec under tests/ui/ or a full user journey under tests/ui/e2e/.
  2. Import test and expect from the UI fixture module.
  3. Use page-object locators and role-based selectors; avoid fixed waits.
  4. Use authenticatedUsersPage when authentication is setup, or loginPage when testing login itself.
import { expect, test } from './fixtures.ts';

test('finds a seeded user', async ({ authenticatedUsersPage, testData }) => {
  const jane = testData.existingUsers.jane;
  await authenticatedUsersPage.searchFor(jane.email);
  await expect(authenticatedUsersPage.getUserRow(jane.name)).toBeVisible();
});

API test

  1. Add a spec under tests/api/.
  2. Use the usersApi fixture so requests are authenticated and response schemas are validated.
  3. Use apiTestUser only for tests that need a record created for the test.
  4. Use graphqlApi for GraphQL; add new operations to graphqlDocuments in the client.
  5. When the client calls a new REST operation, add it to usersApiOperations so the contract test checks it.
  6. Tag data-changing tests @test-data; fixture teardown removes generated users.
import { expect, test } from './fixtures.ts';

test('searches by email', async ({ usersApi, testData }) => {
  const jane = testData.existingUsers.jane;
  const results = await usersApi.searchUsers({ email: jane.email });
  expect(results[0]).toMatchObject(jane);
});

Accessibility, mocked, and known-defect tests

  • Accessibility: request makeAxeBuilder, run await makeAxeBuilder().analyze(), and assert expect(results.violations).toEqual([]). Scope with .include(...) instead of disabling rules.
  • Network failures: request usersApiMock and use fulfill, respondWithUsers, abort, or hold rather than calling page.route() in a spec. Use testData.mockUsers for rows a test edits or deletes, and always mock data resets in UI tests.
  • Known app defects: write the test for the correct behaviour and declare it with test.fail() and an app-defect annotation, inside a known app defects describe block.

Both kinds of test follow docs/test-writing-standards.md. To have tests written for a requirement automatically, use the requirement-to-test orchestrator.

Requirement-to-test orchestrator

The orchestrator is a Claude Code workflow that turns a requirement written in the repository into Playwright tests. You give it a requirement ID. It plans one scenario per acceptance criterion, has a writer agent add the tests, runs them, has a healer agent fix failures, checks the result for flakiness, and then asks you to approve the changes. Nothing is committed or pushed until you approve. 

/requirement-to-test REQ-001

Prerequisites

  • Claude Code, opened at the repository root so it loads .claude/ and .mcp.json.
  • The playwright MCP server from .mcp.json enabled; the agents use it to explore the running app.
  • Framework and app dependencies installed (see Quick start).
  • LOGIN_USERNAME and LOGIN_PASSWORD set in env/.env.local. Without them, authenticated tests skip and the orchestrator reports them as not verified rather than passed.

Writing a requirement

Requirements live in requirement/, one Markdown file per feature, named <ID>-<slug>.md (for example REQ-001-user-search.md). Copy requirement/_template.md to start one; files starting with _ are ignored. The format is described in requirement/README.md. 

---
id: REQ-001
title: Search users by name or email
status: ready        # draft | ready
---

## Description
A signed-in user on the Users screen can narrow the users table by typing in the search box.

## Acceptance criteria
- AC1: Given I am on the Users screen, when I search for part of an existing user's name,
  then only users whose name matches are listed.
- AC2: ...

## Out of scope
- Search through the API or GraphQL.

## Test data
- Use the seeded users from tests/data/; do not create users for these scenarios.
  • Each numbered acceptance criterion becomes at least one test, so write each one as an observable outcome.
  • status: draft makes the orchestrator ask before it continues; set ready when the criteria are final.
  • Generated tests carry the annotation { type: 'requirement', description: 'REQ-001' }, so a requirement's tests can be found by searching for its ID.

How a run works

The orchestrator itself runs in your Claude Code session and makes every decision. It hands two jobs to subagents, each of which starts with a fresh context, does its job, and reports back. The subagents never call each other.

  1. Preconditions.
    Finds the requirement file, checks for uncommitted test changes, and creates the branch tests/req-001.
  2. Read.
    Extracts the numbered acceptance criteria, out-of-scope notes, and test-data hints.
  3. Plan.
    Maps each criterion to a test, file, and tags, and skips criteria existing tests already cover.
  4. Write.
    The writer agent confirms locators in the live app through Playwright MCP, then adds specs, page objects, and data.
  5. Verify.
    Runs Prettier, type checking, lint, and the changed specs.
  6. Heal.
    On failure, the healer agent classifies the cause and fixes test defects only. Up to three attempts.
  7. Stability.
    Runs passing specs with --repeat-each=3; intermittent failures go back to healing.
  8. Approve.
    Shows coverage, the diff, run results, and suspected app defects, then asks you to approve, request changes, or reject.

Healing rules

The healer sorts each failure into one of three kinds and acts only on the first:

ClassificationExamplesAction
Test defectWrong locator, missing wait for a state, data collision between parallel tests, type or lint error.Fixed, following the writing standards.
Application defectThe app does not behave as an acceptance criterion says.No change; reported with expected and actual behaviour.
Environment problemApp not running, missing credentials, port in use, missing browser.No change; reported.
A test is never forced to pass. The healer may not loosen or delete an assertion that encodes an acceptance criterion, add test.skip, test.fixme, or test.fail, add waitForTimeout or force: true, raise timeouts as a fix, swallow errors, or edit app/ or playwright.config.ts. The orchestrator reads the diff after every heal and reverts any weakened assertion.

Approval

ChoiceWhat happens
Approve and commitCommits on tests/<id> with the message test: cover <ID> - <title>. Nothing is pushed.
Request changesYour notes go back to the writer, then the run repeats from verification.
Reject and discardLists and removes the run's changes, switches back to your original branch, and deletes the test branch.

Heal and verification runs use the list reporter, so they do not add entries to the cumulative test history. The orchestrator never edits requirement files; if a requirement is unclear or wrong, it says so in the report.

Continuous integration

The GitHub Actions workflow (playwright.yml) runs on every push except to test-history, on pull requests, and on manual dispatch. It uses Node.js 22 on ubuntu-24.04 with a 30-minute timeout and runs these steps in order:

  1. Check out the repository with submodules, then run git submodule update --remote so the app is tested at the latest main commit (logged in the job output).
  2. Fail early if the credential secrets are missing; install framework dependencies; restore history.json from the test-history branch.
  3. Install app dependencies, then run lint, format:check, and typecheck.
  4. Set short apt timeouts so a slow mirror fails fast, restore cached Playwright browsers, install Chromium with system dependencies (only system dependencies on a cache hit), and run test:history:unit.
  5. Run npm run test:local against http://127.0.0.1:9899.
  6. Upload results and, on non-PR runs, persist history.
GitHub settingValue
Secret TEST_LOGIN_USERNAMETest account username.
Secret TEST_LOGIN_PASSWORDTest account password.

The workflow fails early when test credentials are missing. It installs only Chromium and uploads the Playwright report, JSON results, cumulative history, and failure artifacts. On non-PR runs, it updates the dedicated test-history branch; workflow permissions grant the required contents: write access. Runs are serialized to prevent concurrent history updates.
