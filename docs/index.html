Users App Test Framework

A practical guide to how this TypeScript framework configures environments, runs browser and API tests, manages test data, validates API responses, and organizes its source files.

Playwright Test TypeScript Chromium · Firefox · WebKit Zod API validation

Overview

The framework tests the Users App at the BASE_URL selected for a run. Browser tests cover the home page, login flow, users screen, and a complete login-to-logout journey. API tests cover the documented user endpoints and validate successful response payloads at runtime.

UI tests

Located in tests/ui/; executed in Chromium.

API tests

Located in tests/api/; executed once in the dedicated api project.

Shared code

Page objects, fixtures, test data, factories, API schemas, and environment checks are kept in focused modules.

The Users App is included in app/ as a Git submodule. Initialize it with git submodule update --init --recursive. For loopback targets under TEST_ENV=local or TEST_ENV=test, Playwright starts it with npm --prefix app start and waits for BASE_URL. Remote test, development, and staging targets must already be reachable.

Quick start

  1. Install Node.js 20.19+, 22.13+, or 24+ and npm.
  2. Install framework and bundled app dependencies, then the three browser engines.
  3. Copy an environment example and set the application URL and credentials.
  4. Run the desired test command; Playwright starts the bundled app for loopback targets.
git submodule update --init --recursive
npm ci
npm ci --prefix app
npx playwright install chromium
cp env/.env.example env/.env.local
npm run test:local

For API tests that create or delete users, use a loopback URL with TEST_ENV=local or a dedicated, disposable TEST_ENV=test target with an explicit hostname allowlist.

How a test run works

  1. Select environment.
    TEST_ENV chooses the matching env/.env.* file.
  2. Resolve URL.
    BASE_URL is required except for the local default.
  3. Start local app.
    Loopback targets in the local or test environment start app/; local runs reuse a responding server.
  4. Select project.
    API specs run once and serially because the bundled app uses shared JSON storage; UI specs run in three browser engines.
  5. Set up fixtures.
    Each test receives only the page objects, data, and API client it requests.
  6. Capture diagnostics.
    Failures retain screenshots and video; traces are collected on retries.
  7. Update history.
    Final outcomes update per-test pass rates and the standalone cumulative report.

playwright.config.ts defines projects, reporters, retries, browser settings, output locations, and environment loading. In CI, retries are enabled and test.only is rejected.

Fixtures and lifecycles

API fixtures

  • usersApi reads credentials and authenticates with POST /api/login.
  • testData provides shared, read-only reference values.
  • apiTestUser creates a uniquely named user for one test and deletes it in teardown.

API fixtures are defined in tests/api/fixtures.ts. The API fixture is lazy: it does not log in or create a user unless a test requests it.

UI fixtures

  • loginPage and usersPage construct page objects for the current test's page.
  • authenticatedUsersPage logs in and verifies navigation to the users screen.
  • Every test receives an isolated Playwright page/context; authentication is performed per test.

UI fixtures extend the API fixtures in tests/ui/fixtures.ts. Authenticated tests are skipped when credentials are not configured.

API client and response validation

UsersApiClient centralizes authenticated requests for list, search, count, create, retrieve, update, and delete operations. Its successful JSON responses pass through parseApiResponse.

Runtime contracts are declared with Zod in tests/api/utils/schemas.ts: login API key, individual user, user list, and user count. A response with an unexpected status, invalid JSON, or invalid payload shape fails with endpoint context. Unmodeled user fields are stripped from the parsed result.

API scenarios live in tests/api/users.api.spec.ts. They verify listing, search, count, retrieval, update, and deletion. CRUD tests use a generated user and are tagged @test-data.

API contract note: The app's current raw user response includes a password property. The test schema does not expose that unmodeled property, but the application should avoid returning credentials in API responses.

Test data and safety rules

  • tests/data/users.ts contains typed reference data.
  • createUniqueUserData generates collision-resistant users for CRUD tests.
  • environment.ts reads credentials and guards mutation targets.
  • @test-data marks tests that create or delete application records.

The apiTestUser fixture creates and cleans up records only for loopback hosts under TEST_ENV=local or hostnames listed in TEST_DATA_ALLOWED_HOSTS under TEST_ENV=test. Development and staging scripts exclude tests tagged @test-data. Do not configure a production host as a test-data target.

Cumulative test history

Each Playwright run writes raw JSON results to test-results/results.json, updates the local .playwright-history/history.json store, and generates reports/test-history-report.html plus separate per-test history and recent runs pages under reports/, linked from the report header. The standalone HTML pages can be regenerated with npm run test:history:report.

  • Tests are identified by project, spec path, and full title path, so moving a test's source line does not reset its history.
  • Pass rate is passed divided by passed plus failed; skipped tests are shown separately and excluded.
  • A pass after a retry counts as passed and is also marked flaky.
  • Per-test totals are all-time; the latest 100 run summaries and 30 outcomes per test are retained.
  • The metrics landing page includes KPI cards, a pass-rate trend for up to 12 runs, and the latest run's outcome breakdown.

Use the report controls together to search scenario titles, spec paths, projects, and tags; filter by UI, API, or E2E category; select a latest status or a tag; and reset all filters. The Flaky status isolates tests whose latest result passed after retry.

The local history directory and generated HTML are Git-ignored. CI restores and updates history.json on the dedicated test-history branch, and uploads the HTML report pages with the run artifacts. The first non-PR run creates the branch. Repository Actions settings must allow the workflow's contents: write permission; pull-request runs do not write to the branch.

Adding tests

UI test

  1. Add a spec under tests/ui/ or a full user journey under tests/ui/e2e/.
  2. Import test and expect from the UI fixture module.
  3. Use page-object locators and role-based selectors; avoid fixed waits.
  4. Use authenticatedUsersPage when authentication is setup, or loginPage when testing login itself.
import { expect, test } from './fixtures.ts';

test('finds a seeded user', async ({ authenticatedUsersPage, testData }) => {
  const jane = testData.existingUsers.jane;
  await authenticatedUsersPage.searchFor(jane.email);
  await expect(authenticatedUsersPage.getUserRow(jane.name)).toBeVisible();
});

API test

  1. Add a spec under tests/api/.
  2. Use the usersApi fixture so requests are authenticated and response schemas are validated.
  3. Use apiTestUser only for tests that need a record created for the test.
  4. Tag data-changing tests @test-data; fixture teardown removes generated users.
import { expect, test } from './fixtures.ts';

test('searches by email', async ({ usersApi, testData }) => {
  const jane = testData.existingUsers.jane;
  const results = await usersApi.searchUsers({ email: jane.email });
  expect(results[0]).toMatchObject(jane);
});

Continuous integration

The GitHub Actions workflow installs the bundled app, runs lint, formatting, and type checks, then runs the full suite against it.

GitHub settingValue
Secret TEST_LOGIN_USERNAMETest account username.
Secret TEST_LOGIN_PASSWORDTest account password.

The workflow fails early when test credentials are missing. It installs Chromium and uploads the Playwright report, JSON results, cumulative history, and failure artifacts. On non-PR runs, it updates the dedicated test-history branch; workflow permissions grant the required contents: write access. Runs are serialized to prevent concurrent history updates.

Keep this guide aligned with the test fixtures, API schemas, and commands whenever the framework structure changes.
